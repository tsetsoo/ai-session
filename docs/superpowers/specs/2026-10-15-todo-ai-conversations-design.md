# Todo AI Conversations Design

**Date:** 2026-10-15  
**Status:** Draft  
**Repos:** todo-app (this spec: data + API), ai-session-remote (host script + native client, follow-up spec)

## Goal

Every section (Sp / I / Si / P) is assigned a computer, and every todo can have one AI coding conversation (Claude Code in tmux) running on its section's computer. Todos and their conversations are reachable from a native SwiftUI app on iPhone and Mac.

## Principles

- **todo-server only stores data.** It never opens SSH connections, never spawns processes, and never relays terminal bytes. Latency-sensitive traffic goes client → computer directly.
- **Clients connect directly** to the computer over SSH (Tailscale), reusing ai-session-remote's pooled SwiftNIO SSH + SwiftTerm stack.
- **tmux is the runtime source of truth**; todo-server is the source of truth for *which* conversation belongs to *which* todo.
- Section codes `Sp`, `I`, `Si`, `P` are opaque labels. No expanded names anywhere (UI, API docs, describe output).

## Context (current)

- todo-server: Actix-web + SQLite on the Pi (`100.118.255.23:8080`, Tailscale), no auth, CORS open, WebSocket refresh pings on every mutation.
- `todos.section` is one of `Sp`/`I`/`Si`/`P` (CHECK constraint). Sections are the todo types.
- ai-session-remote: iOS-only SwiftUI app; SSH straight to hosts; sessions are tmux `ai/<tool>/<slug>`; no backend; no Claude session tracking.
- `describe.rs` currently expands section codes into guessed names — to be removed.

## Product decisions

| Topic | Decision |
|---|---|
| Todo type | = section (`Sp`/`I`/`Si`/`P`); no new type entity |
| Computer per type | Each section maps to at most one computer + default working dir + tool |
| Conversation per todo | At most one; created on first open, resumed afterwards |
| Moving a todo to another section | Existing conversation stays where it is (computer + cwd snapshotted at creation) |
| Completing / deleting a todo | Conversation record kept on complete; deleted on todo delete. Killing tmux is a client action |
| Backend role | Data store only (no SSH, no terminal relay) |
| Clients | Native SwiftUI (iPhone + Mac). Existing Leptos web UI keeps working for plain todos; no browser terminal |
| Terminal engine | SwiftTerm now, behind a renderer seam; libghostty is a later option |

## Data model

### `computers`

```sql
CREATE TABLE IF NOT EXISTS computers (
  id         TEXT PRIMARY KEY,            -- uuid v4
  name       TEXT NOT NULL,
  hostname   TEXT NOT NULL,               -- Tailscale name or IP
  port       INTEGER NOT NULL DEFAULT 22,
  username   TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

No keys or secrets are stored. Clients match a computer to their locally stored SSH host by `hostname` + `port` + `username`.

### `section_computers`

```sql
CREATE TABLE IF NOT EXISTS section_computers (
  section     TEXT PRIMARY KEY CHECK(section IN ('Sp','I','Si','P')),
  computer_id TEXT NOT NULL REFERENCES computers(id) ON DELETE RESTRICT,
  cwd         TEXT NOT NULL,              -- default working dir, e.g. ~/programming
  tool        TEXT NOT NULL DEFAULT 'claude' CHECK(tool IN ('claude'))
);
```

`tool` is only `claude` in v1 (resume by session id is Claude-specific); widened later.

### `conversations`

```sql
CREATE TABLE IF NOT EXISTS conversations (
  todo_id           TEXT PRIMARY KEY REFERENCES todos(id) ON DELETE CASCADE,
  computer_id       TEXT NOT NULL REFERENCES computers(id) ON DELETE RESTRICT,
  cwd               TEXT NOT NULL,        -- snapshot at creation
  tool              TEXT NOT NULL,        -- snapshot at creation
  tmux_name         TEXT NOT NULL UNIQUE, -- ai/claude/todo-<first 8 of todo id>
  claude_session_id TEXT NOT NULL UNIQUE, -- uuid v4, generated by server
  status            TEXT NOT NULL DEFAULT 'unknown' CHECK(status IN ('busy','waiting','idle','unknown')),
  status_message    TEXT,
  status_updated_at TEXT,
  created_at        TEXT NOT NULL DEFAULT (datetime('now'))
);
```

`tmux_name` uses the first 8 hex chars of the todo id; on a UNIQUE conflict, fall back to the full id. This stays within ai-session-remote's slug rule (`[a-z0-9-]+`), so these sessions also appear in its existing session list.

## API

All new endpoints require `Authorization: Bearer <TODO_API_TOKEN>` (env var on the server). See open questions for existing endpoints.

| Method | Path | Purpose |
|---|---|---|
| `GET/POST` | `/api/computers` | List / create |
| `PATCH/DELETE` | `/api/computers/{id}` | Update / delete (409 if referenced) |
| `GET` | `/api/sections/computers` | All four section → computer mappings |
| `PUT/DELETE` | `/api/sections/{code}/computer` | Set / clear mapping (`{computer_id, cwd, tool}`) |
| `GET` | `/api/todos/{id}/conversation` | Conversation + computer, 404 if none |
| `POST` | `/api/todos/{id}/conversation` | Idempotent get-or-create. 409 if the todo's section has no computer |
| `DELETE` | `/api/todos/{id}/conversation` | Forget record (client kills tmux first) |
| `GET` | `/api/conversations` | All conversations with status (for badges / lists) |
| `POST` | `/api/conversations/status` | Hook endpoint: `{claude_session_id, status, message?}` |

- `Todo` responses gain an optional `conversation_status` so lists can show badges without N+1 calls.
- Every mutation (including status) triggers the existing WebSocket broadcast.
- Shared request/response types go in `todo-shared`.
- `/api/describe` is updated: new endpoints listed, section codes shown without expansions.

## Host contract (implemented in ai-session-remote)

**Open script** — `~/.ai-remote/bin/ai-todo-open <tmux_name> <cwd> <claude_session_id>`:

```sh
tmux has-session -t "=$1" 2>/dev/null && exec tmux attach -t "=$1"
case "$2" in "~"*) set -- "$1" "$HOME${2#\~}" "$3" ;; esac   # cwd is stored with ~
cd "$2" || exit 93
if [ -n "$(find ~/.claude/projects -name "$3.jsonl" 2>/dev/null | head -1)" ]; then
  exec tmux new-session -s "$1" -c "$2" -- claude --resume "$3"
else
  exec tmux new-session -s "$1" -c "$2" -- claude --session-id "$3"
fi
```

One command covers create, attach, and resume after tmux died or the machine rebooted. Clients run it as the PTY command over SSH.

**Status hooks** — in `~/.claude/settings.json` on each computer, `UserPromptSubmit` → `busy`, `Notification` → `waiting`, `Stop` → `idle`. Each hook reads `session_id` from its stdin JSON and `curl`s `POST /api/conversations/status` with the bearer token. Sessions that are not todo conversations get a 404, which the hook ignores.

## Clients (follow-up spec in ai-session-remote)

- Add a hub client to `AISessionCore`.
- Add a Todos screen grouped by `Sp`/`I`/`Si`/`P`, with status badges and live refresh via `/api/ws`.
- Opening a todo calls `POST …/conversation`, then opens the existing terminal screen running `ai-todo-open`.
- Add a macOS target. Only 3 files use UIKit; branch them with `#if os(...)` and use a three-column layout (sections | todos | terminal).
- Terminal polish: a shipped `tmux.conf` snippet (`escape-time 0`, true color, `extended-keys on`, `set-clipboard on`, `focus-events on`, mouse), native notifications on `waiting`, ⌘1–9 shortcuts, a `TerminalRenderer` seam.

## Implementation order

1. todo-server:
   - Schema plus migrations.
   - Shared types.
   - Endpoints.
   - Bearer token.
   - Tighten CORS.
   - Update describe (removing the section expansions).
   - Tests in the style of `daily.rs`.
2. ai-session-remote/scripts:
   - `ai-todo-open`.
   - The hook script.
   - An installer that drops both into place, merges the hooks, and appends the tmux.conf snippet.
3. Swift app (iOS): hub client, Todos screen, opening a conversation.
4. Swift app (macOS) target.
5. Later:
   - Push notifications.
   - Transcript preview (read the `.jsonl` over SSH).
   - Mosh-style local echo for iPhone.
   - libghostty experiment.

## Open questions

- **Auth for existing todo endpoints.** Proposal: v1 leaves the existing endpoints open (Tailscale only) so the web UI is unchanged; only the new endpoints need the token. Alternative: token everywhere, with the web UI asking for it once.
- **Kill on complete.** Should completing a todo also offer to kill its tmux session? Proposal: the client shows a "close conversation" action, with no automatic kill.

## Non-goals (v1)

- Server-side SSH, terminal relay, or a browser terminal.
- Multiple conversations per todo.
- Tools other than Claude Code.
- Storing SSH keys on the server.
